# Stripe v1

Status: done and reference-enabled after full combined lifecycle, browser and canonical production/CI acceptance. Clean consumers remain opt-in. See [evaluation](../../docs/evaluations/STRIPE_MODULE_EVALUATION.md) for the accepted implementation revision and fixture limits.

Stripe is independently optional (`defaultInstalled: false`), requires Jobs and Webhooks, and targets stripe-node 23.0.0 / request API `2026-09-30.endive`. Hosted Checkout payment mode supports approved existing one-time Prices and already-bound customers. It does not implement subscriptions, refunds, manual capture, payouts, Connect, card handling or financial policy. Identity/Organizations, Audit Log and Notifications remain optional application wiring.

Stripe owns financial state. The application owns approved offers, explicit local bindings, authorization, fulfillment, operation/inbox history and minimal projections. Metadata, redirects and callback signatures never establish local ownership or payment success. A completed Checkout can remain unpaid. This implementation performs no fulfillment.

## Configuration and trusted application seams

Configuration is lazy: `STRIPE_SECRET_KEY`, `STRIPE_ACCOUNT_ID`, `STRIPE_MODE` (test default), `STRIPE_WEBHOOK_SECRET`, optional `STRIPE_WEBHOOK_SECRET_PREVIOUS`. Mode must match secret/restricted keys and verified events; publishable keys are rejected. Live mode requires an explicit server deployment assignment. The operator independently configures the webhook endpoint API version; SDK pinning does not configure it. Missing provider configuration does not affect build, app/worker startup or health; explicit configured operations return safe 503.

`createStripeCapability(wiring)` supplies `authorizeScope`, `authorizeBoundResource`, `authorizeReconciliation`, `resolveOffer`, `approvedRedirects`, optional `resolveConnection`, the application Drizzle database and transactional existing-Jobs enqueue adapter. Authorization denies when its seam is absent. Context is server-only after native authentication. User scope must match its actor; tenant scope requires current application membership policy. Root permits only current local user owners and has an empty approved-offer registry until deployment supplies existing vetted Price IDs and redirect URLs. Browser input cannot select remote IDs, endpoints, keys, account/context headers or a tenant.

`createBindingInTransaction` and `retireBindingInTransaction` are trusted server extensions. Bindings connect local UUIDs/scope/resources to registered connections and remote identity; callbacks cannot create arbitrary bindings. Only a trusted originating Checkout operation can create a Checkout child; an authoritative GET of an existing bound Checkout can acquire its PaymentIntent child. Retired bindings return 404. Provider/customer registration is separate operator work.

## Native reference API and UI

TanStack Start POST routes under `/api/integrations/stripe/{action}` restore the native session and enforce the configured origin. Actions are `requestCheckout`, `getOperation`, `getCheckout`, `requestPaymentReconciliation`, `listPayments`, and queued-only `cancelOperation`. Unknown object keys fail validation. UI at `/app/payments` shows local status, accepts local customer/registered offer references, preserves an idempotency key across repeated identical selection, polls operations and permits cancellation before dispatch. Canceling HTTP does not prove that a durable operation or financial write was undone. An authorized open Checkout getter alone exposes a validated HTTPS `checkout.stripe.com` URL; lists, operations and Jobs never contain it.

The independent add-on supplies server primitives and default-denied Jobs wiring without importing Auth/Organizations or mounting human routes. Applications compose native routes/server functions after their own authentication. No general-purpose router, provider loader, universal billing abstraction or second queue is introduced.

## Durability, retries and privacy

Convenience command methods own one short transaction and return only after commit. `createBindingInTransaction`, `retireBindingInTransaction`, `receiveInTransaction`, and worker recovery accept caller-owned transactions: helpers never commit, roll back, reconnect or retry them. Transactional Jobs handoff uses the existing same-database guard. No provider HTTP call is held inside a database transaction.

Scoped operation keys and normalized input digests reject changed intent and return the original safe state for duplicates. Existing customer, Price lines and approved redirects are frozen privately before dispatch. Dispatch persists its UUID token/first-attempt timestamp before transport. SDK retries are zero and telemetry is disabled; each operation owns an official FetchHttpClient with streaming response bounds and cancellation. Jobs uses five retries, 30-second exponential backoff capped at 15 minutes. Safe write replay uses the identical `gs-stripe:<operation UUID>` key and frozen parameters strictly before first dispatch +23h. It never creates a new key to escape a cached failure. At/after the cutoff, account assignment changes, exhausted ambiguity or expired write leases require reconciliation. Post-dispatch uncertain writes cannot be marked cancelled.

Per-binding PostgreSQL leases/revisions and token-fenced short commits serialize reconciliation. Workers recheck the stored human actor/current scope for user operations. Callback workers use explicit trusted `authorizeReconciliation(binding, signal)` and never invent a human from metadata. Authoritative GETs update projections independently of hint order. Recovery is an explicit bounded `recoverInTransaction` call, never startup network I/O or a new daemon.

Raw bytes are bounded and verified with the pinned SDK's Stripe-Signature verifier before parsing. Current/previous secrets, multiple v1 signatures and an absolute 300-second timestamp window are supported. API-v1 snapshot events cover the six Checkout/PaymentIntent events in the contract. Account/mode/context mismatches reject; authenticated unsupported version/types and unbound resources are ignored durably. Receipt identity is expected account/mode/native event ID. First body digest is retained on identity collisions, without retaining either body. Receipt and ID-only enqueue are atomic. Durable duplicates/ignored hints return 200 `{accepted:true}`, not a claim of domain completion.

Only allowlisted projection/operation fields and static safe errors cross public boundaries, with no-store. Provider bodies, contacts, financial responses, URLs, secrets and headers are excluded from logs/queue payloads. Private immutable dispatch intent is retained only in the local ledger. Amounts are nonnegative safe integer minor units; unknown statuses serialize as `unknown`. Lists use scope-filtered descending `(createdAt,id)` keysets, default25/max100 and strict canonical versioned base64url cursors.

## Packaging, migration and removal

Install the authored/compiled add-on through the generic catalog harness: `bun run add-ons:compile stripe`, `bun run add-ons:test stripe`. Custom dependency resolution uses the existing generic CLI URL server. The clean fixture runs local protocol/persistence proof on pinned Bun and actual Node24, builds, explicitly removes Stripe runtime/registration/package, rebuilds and checks retained data while keeping Jobs/Webhooks.

Root additive migrations `0011_stripe_v1.sql`, `0012_stripe_recovery.sql` and `0015_stripe_receipt_conflicts.sql` occupy combined journal indices 9–11 and cumulative snapshots `0009_snapshot.json`–`0011_snapshot.json`. Snapshot 0009 follows Invoice Ninja snapshot 0008; all retain the baseline and preceding provider schema. The eight baseline SQL files, journal entries/timestamps and hashes are preserved. Filename prefixes and journal indices intentionally differ; Medusa follows at indices 12–13. Clean consumers receive Stripe-only SQL at indices 0–2. Review branch-specific deployed histories before upgrading instead of rewriting applied history. Run explicit app migrations and Jobs migration/doctor before app/worker; neither starts by migrating or contacting Stripe.

For removal, first stop producers and Stripe processing, settle or expire attempts and recover ambiguous ledgers. Remove native routes, Payments page/navigation, root `src/lib/stripe.server.ts`, the `referenceStripeJobs` registry import/spread, operational scripts and the `stripe` runtime dependency. Retain `schema.ts`, `contract.ts`, database schema exports, SQL/journal/snapshots, bindings, projections, ledgers and inbox history. Their retained schema has no Stripe runtime import. Auth/Jobs/Webhooks and remote resources remain. Callback deregistration, credential revocation, provider deletion and destructive local purging are separate explicitly authorized operator actions; no CLI transactional uninstall claim is made.

## Compatibility and verification

Local wire and disposable PostgreSQL fixtures establish protocol behavior only. No Stripe CLI login, remote account/credential creation, webhook registration, sandbox/live API call, payment, operator deployment or financial certification is implied. All contract fixtures, development/production browsers, canonical image/migrations/health/standalone worker, root checks and hosted CI passed at the combined implementation revision linked in the evaluation. Future changes require the same complete exact-head gates; local fixtures or package manifest support alone are insufficient.

Root-only `stripe:migrations` checks seeded upgrades/historical hashes; `stripe:worker` runs the actual existing standalone Jobs worker against its own disposable database. The generic consumer fixture additionally tests native worker denial with no application authorization seam and retention of bindings, projections, operations and inbox rows. Callback failures can be repaired once with trusted server `repairInboxInTransaction`; duplicate repair does not enqueue again. Cached500 replay stays on the original key; definitive provider rejections fail safely, while timeout/disconnection/cancellation after dispatch retains uncertainty.

Accepted Checkout IDs are persisted privately before projection commit. Trusted server-only `requestOperationReconciliation` requeues a known accepted session or explicitly selected existing session for authoritative GET, verifying the original bound customer, mode/account and frozen currency; it has no browser route and never retries creation beyond23h. A crash before that ID is durably recorded remains an unknown outcome requiring a trusted operator decision.

Authenticated same-event-ID/different-digest receipts retain the original body hash and bound resource. One new conflicting digest coalesces a current-state recheck; active processing records one atomic follow-up. No replacement hint establishes ownership. Additive `0015_stripe_receipt_conflicts.sql` preserves already-authored `0011`/`0012`; `0013`/`0014` belong to Medusa and follow Stripe in the combined journal. Existing data and all provider Jobs rows remain after removal.
