# Medusa v1

Status: in progress pending complete release verification. A disposable pinned Medusa 2.21.2 backend verifies native Admin GET authentication, products/orders/pages, exact totals, native product workflow subscriber delivery and source-matched order.placed event-bus delivery, followed by durable receipt/Jobs handoff and the actual standalone Node24 fixture worker consuming private existing Jobs payloads. No checkout/payment workflow or external provider was exercised. See [evaluation](../../MEDUSA_MODULE_EVALUATION.md). No readiness promotion, deployment or publication is part of implementation.

## Boundary and installation

An independent optional TanStack custom add-on, `medusa`, with hard dependencies `postgres-jobs` and `webhooks`. Clean consumers retain `defaultInstalled:false`. Object Storage, Organizations and Search are optional application wiring; no imports or required providers are added. The root reference restores Better Auth sessions in native TanStack Start HTTP routes, supports user scopes only, and exposes `/app/medusa`. Tenant use requires explicit current membership policies and otherwise denies. Native route handlers serve `/api/integrations/medusa/$`; removing that route disables provider HTTP behavior.

The provider owns commerce. This integration performs only Admin GETs for authorized, explicit server-owned product/order bindings, local projection queries and queued reconciliation. It does not create products, orders, carts, payments, refunds, fulfillment, customers or credentials. Browser input never chooses endpoints, keys, connection IDs, remote resource IDs or sales channels. Trusted server binding creation and retirement live in `bindings.server.ts`. Scope and remote identity uniqueness prevent callbacks from assigning ownership. Foreign/retired bindings return404. Bindings retire rather than remap.

Compile: `bun run add-ons:compile medusa`. Install through the pinned official CLI and generic lifecycle: `bun run add-ons:test medusa`; the catalog controls generic Bun/Node24 CI discovery even while verification is in progress. Reviewed overlays preserve starter.echo and Webhooks jobs, and explicitly include the schema in Drizzle configuration. The clean adapter denies every ownership/reconciliation policy until the application supplies them; Auth/Organizations are not mandatory package imports.

## APIs and policies

`createMedusa({db,enqueue,policy})` exposes getProduct/getOrder, listProducts/listOrders, requestResourceReconciliation, requestSyncPage, getOperation and pageResult. Getters read local projections only; refresh is explicit. Lists default25/max100, descending immutable(createdAt,bindingId), canonical versioned base64url cursors and scope filters on every page. Inputs reject unknown keys. Page results expose only processed count and next cursor. Each provider page is bounded100, advances by returned page length, and never auto-continues. Pagination is not a snapshot/export; partial progress is retained on failure, and failed page operations require an explicit fresh request rather than hidden replay.

Scope, bound-resource and Medusa-resource policy seams deny by default and are checked before fetch and before projection commit. Callback workers use separate trusted `authorizeReconciliation(binding,signal)`, deny by default, with no invented human actor. The root authorizes callbacks only for an active server-owned user binding and an existing local user. Connection resolution defaults to one lazy environment connection, or an explicit trusted `resolveConnection`. No provider loader or optional identity dependency.

## Configuration and bounds

`MEDUSA_BASE_URL`, `MEDUSA_SECRET_API_KEY` are required only when used. Missing config returns safe503 and never prevents startup. Optional `MEDUSA_BRIDGE_WEBHOOK_SECRET` and `MEDUSA_BRIDGE_WEBHOOK_SECRET_PREVIOUS` enable the receiver, using whsec_ base64-byte form. Missing bridge secret disables the receiver with503. HTTPS only, except original literal127.* / ::1 hosts in development/test; hostname/numeric aliases, credentials, fragments and redirects reject. Request authentication is Basic base64(key+":"); no obsolete v1 token header or password login.

Outbound15s, worker45s, inbound raw verification/receipt5s; caller cancellation aborts native fetch and remains active through streaming consumption. Provider body2MiB, webhook1MiB, public JSON256KiB, relevant headers8192 bytes (existing verifier additionally bounds signatures4096). No auto pagination/HTTP retries; typed transient reads use existing Jobs five retries,30s exponential/max900s. Errors have static code/message/retryable fields. Results are no-store. Jobs carries only operationId/inboxId and a closed status/error-code output. No payload/response/contact/URL logging.

Product projections select title/handle/status/source/sync times/deleted only. Order projections select status and closed payment/fulfillment enums/currency/exact major-unit total/source/sync times/deleted. Numeric response lexemes are preserved before JSON parsing; unsafe numeric JS values/exponents/overflow reject. Totals never convert through binary float or divide by100. Unknown provider enums become unknown; no contact/address/email/metadata/image URLs or raw provider JSON is persisted or serialized.

## Persistence, workers and recovery

Four application-included Drizzle tables own bindings, minimal JSON projections, operation ledger and inbox. UUIDv4 IDs and timestamptz(3); committed additive SQL `0013_medusa_v1.sql` and `0014_medusa_receipt_conflicts.sql` retains the frozen main's eight migrations exactly. Branch-local contiguous idx8/9 metadata is provisional; parent regenerates combined provider metadata in reserved order. Prefix0008 remains unused. App/worker startup never migrates. Explicit app `db:migrate`, Jobs `jobs:migrate`, then `jobs:doctor` remain required.

Convenience commands explicitly own a short transaction. `*InTransaction` methods use the caller transaction and never commit/rollback/reconnect/retry it. Enqueue must use existing same-database Jobs routing guard/Drizzle adapter. Receipt and enqueue are atomic. Raw bytes are dropped after verification; receipts retain only connection/event identity/hash/minimal bound hint/state. Duplicate supported receipts return200 with no enqueue storm; a differing-digest collision retains the first identity/hash and reconciles that original bound resource, remembering the last conflicting hash and requeueing once if a hint races active processing; unsupported/unbound authenticated events are durably ignored. Latest GET is authoritative, regardless of hint order or repeated IDs.

Per-binding database leases/revisions fence reconciliation; HTTP runs outside SQL transactions. Projection and individual operation/inbox completion share a short transaction. Bound resource/current authorization is rechecked before commit. Confirmed authenticated404 retains safe tombstone values;403/transient errors never establish deletion. Key visibility changes require operator consideration. `recover(limit)` is an explicit bounded server/operator API for expired read attempts; no new daemon/startup network. `retryReceiptInTransaction` transactionally repairs a failed receipt once. Queued operation cancellation prevents dispatch; request cancellation after enqueue requires querying current operation state.

## Application-owned subscriber bridge

Protocol name: application-bridge.standard-webhooks-v1. Commerce hints are not native Medusa-signed webhooks; Cloud build/deployment signatures are out of scope. Receiver POST `/api/integrations/medusa/webhooks/{registeredConnectionId}` verifies raw HMAC id.timestamp.body with existing webhook-id/timestamp/signature verifier,300s absolute window,current/previous secrets. Version1 minimal event id must match webhook-id; type/kind agree. Supported events: product.created/updated/deleted and order.placed only. No metadata ownership or automatic binding.

`bridge/subscriber.ts.example` is an explicitly operator-installed artifact in the separate pinned Medusa project. Vendor producer.server.ts, contract.ts, transport.server.ts and the existing Webhooks protocol alongside it, adjust local imports, and configure MEDUSA_BRIDGE_TARGET_URL/CONNECTION_ID/WEBHOOK_SECRET. Do not copy starter DB/service imports. A retained delivery ID can be reused for in-process retry; a native subscriber retry may create another ID. Provider event infrastructure owns durability. No universal durable-outbox/exactly-once claim; explicit/page reconciliation repairs missed hints.

## Removal and verification

Stop producers and workers first; settle or expire active45s leases, inspect ledger/inbox and then remove Medusa handlers/routes/UI/application wrapper and registry spread. Retain schema declarations, additive SQL/journal history, bindings, projections, operations and inbox. Keep Jobs/Webhooks. No remote callback removal, deletion, credential revocation or resource mutation occurs implicitly. Those are separately authorized operator actions. Canonical schema and required projection type/validation declarations may remain without runtime routes.

`medusa:compat` installs Medusa2.21.2 ONLY in an owned disposable fixture directory, migrates its own provider DB, seeds a fixed local test configuration (no key-minting API), seeds products/orders, installs the application bridge and checks native GETs/subscriber delivery. Native event bus is in-process in this fixture; production delivery durability remains operator infrastructure. It disables provider telemetry and cleans up only its own processes/databases/directory. `medusa:unit` runs local protocol/privacy/cancellation fixtures. `medusa:smoke` creates/drops ONLY its own UUID-named PostgreSQL18 database, applies/repeats migrations, explicitly migrates its Jobs schema and verifies receipts, scopes, rollback, leases, authorization revocation, tombstones and retained history. Generic lifecycle executes protocol+database fixtures under pinned Bun and actual Node24, builds installed consumer, removes Medusa runtime, rebuilds and checks retained tables in the same disposable DB. Tests need a disposable-fixture admin PostgreSQL URL; never production. No transient execution diary belongs here; PR contains exact SHA/command evidence.
