# Cache / Coordination module evaluation

## Research and selection (2026-09-30)

Official [Valkey release metadata](https://github.com/valkey-io/valkey/releases/latest) reported stable [9.1.2](https://github.com/valkey-io/valkey/releases/tag/9.1.2), published 2026-09-01. The actual pulled official Docker image is `valkey/valkey:9.1.2-alpine@sha256:48332870af354a799964c0012ae1194a0bf2bf894eb508f945810596dc2d8d11`. No `latest` or floating minor tag. Registry metadata reported [redis 6.3.0](https://registry.npmjs.org/redis/6.3.0), engine Node >=20, and [ioredis 6.0.0](https://registry.npmjs.org/ioredis/6.0.0), also Node >=20. Node 24 is within the supported engine contract.

Selected current stable `redis` / node-redis 6.3.0. Reviewed upstream [README](https://github.com/redis/node-redis), [configuration](https://github.com/redis/node-redis/blob/master/docs/client-configuration.md), [pub/sub](https://github.com/redis/node-redis/blob/master/docs/pub-sub.md), and installed 6.3.0 API/source for command timeouts and lifecycle. It cleanly supports Redis protocol GET/SET/DEL, NX/EX/PX, INCRBY, EVAL, PING, dedicated pub/sub, byte replies, TLS and supported close/destroy/reconnect. Its upstream advertised test matrix concerns Redis; our real Valkey suite is the evidence for Valkey compatibility, not an invented blanket upstream guarantee. TLS certificate verification is explicitly true for rediss; localhost fixture uses plain redis.

Alternatives: ioredis is mature and suitable, but provides no material improvement for this single-backend primitive. Its common offline queue/retry behaviors would also need deliberate bounds; switching by habit adds no benefit. Valkey GLIDE is the Valkey-native option, useful for advanced cluster/replica routing; its native engine/platform packaging adds complexity for a small standard Node/TanStack add-on, with no needed capability advantage here. Bun's built-in Redis client would couple runtime behavior to Bun while production runs Node 24. No general client benchmark or claim that alternatives are inferior is made.

## Portable subset and limits

Explicit RESP2, ordinary Redis-compatible commands and small private Lua scripts, no module commands, cluster-specific behavior, provider admin API, arbitrary EVAL or client escape hatch. Valkey is actually tested. A second Redis implementation in CI is not tested; provider authentication/TLS are operator configuration, not a claim of certified SaaS compatibility. Cluster, Sentinel and quorum are outside v1.

Configuration/client creation are lazy until first operation, including explicit createCache. URL supports redis/rediss with auth; it never enters browser env or telemetry. Prefix default app:, 1–64 bounded printable ASCII subset; logical names 1–256 same subset. Physical data/lease/channel separation avoids accidental data operations clobbering coordination. Default TTL 300 seconds, per-call/config bound 1–604800 seconds. Explicit setWithoutExpiry only; all lease writes expire, 100–300000 ms. Strings/bytes only, default max 1 MiB with conservative 16 MiB ceiling; outgoing encoded sizes bounded. No unsafe JSON typing.

## Atomic increment and lease review

Increment Lua uses GET to verify existing integer/safe-number range before mutation, INCRBY then EXPIRE only when PTTL is negative. Script execution is atomic; concurrent first increments cannot leave immortal counters. Existing positive TTL is preserved; existing non-expiring integer receives a TTL. Overflow or invalid value fails before modifying data. Required ttlSeconds prevents implicit unbounded coordination. No scripts/results/data enter error messages or telemetry.

Lease acquisition SET random 256-bit token NX PX; atomic token-checked PEXPIRE/DEL for renew/release. Wrong or expired holder cannot touch a replacement. Separate lease namespace plus no arbitrary command exposure protects accidental deletion by normal get/set/delete. It is single-backend advisory coordination, no Redlock/quorum/fencing, no automatic renewal. Pauses, eviction, restarts and partitions can exceed leases; irreversible external effects require DB uniqueness/transactions or real fencing. Timeouts can leave unknown outcomes; do not blind-retry increments/publish/external effects. A lease whose acquire response is lost expires by its bounded TTL.

## Pub/sub and lifecycle

One dedicated client per subscription, maximum 32; exact channels, bounded bytes, handler errors contained without unsafe logs. No persistence/replay, subscribers may miss messages while disconnected; subscriber count is not processing acknowledgement. Supported reconnect resubscribes during bounded retry window; consumers explicitly recreate subscriptions after exhaustion. Handler workloads belong to consumer lifecycle, not cache shutdown.

Initial complete connect <=3 seconds by default, configurable <=10 seconds; supported client queue timeout plus explicit response deadline default 2 seconds, configurable <=10 seconds. Installed node-redis 6.3.0 clears the native timeout after writing, so the private command wrapper races the response and destroys the connection on expiry; a real CLIENT PAUSE fixture proves this bound and recovery. This closes outstanding waits without replay; concurrent requests on that connection may also fail. Pub/sub acknowledgements additionally use explicit bounds because their internal command path is separate. Supported exponential reconnect six retries, backoff capped at 1 second, authentication stops immediately. Offline queue disabled; no automatic replay of commands after reconnect, accepted queue capped at 1024. close rejects new calls, bounds drain and close then force-destroys connections; caller owns graceful application drain. Import/build/start never contacts Valkey. No readiness addition.

CacheError exposes only reviewed codes/static messages and safe inspection/JSON; original non-enumerable cause remains server-side. Node-redis error listeners never log raw exceptions. Avoid automatic command diagnostics instrumentation that could capture arguments. Optional observer gets bounded signals only and cannot alter operation success/failure. Reference wrapper emits `app.cache.*` operations/outcomes, durations, hit/miss, numeric sizes, no key/prefix/channel/token/URL/message/value/user label. Reusable assets import no Observability.

## Infrastructure, packaging, composition

Separate additive Compose pins Valkey image/digest, loopback port, no authentication for disposable local service, no AOF/RDB, tmpfs /data overriding image's volume declaration and no named volume. Normal production Compose is unchanged. Real compatibility creates a unique project/free port, uses only unique prefix/exact cleanup, restart/recovery is permitted only for that disposable project, and teardown runs finally. Smoke never restarts a user service. Check only PING.

Official TanStack add-on has no framework dependsOn or reusable requires; assets, manifest, .cta, retained distributable and clean fixture are together under capabilities/cache-coordination. Reference app opt-in is separate from generated defaults (false). No Drizzle/Auth/Jobs dependency, migrations, UI, worker or other capability status change. Clean fixture typechecks and backendless-builds without Cache config/service, runs actual Valkey, removes runtime/package/env additions, and builds again. App removal and pruning authoring source are separate; no uninstall transaction or remote destruction. Future API shared rate-limit state, Jobs ephemeral coordination (durable jobs stay PostgreSQL), and Realtime pub/sub are documented only.

Before external publication: versioned URL/release contract, license and dependency advisories, runtime/service/auth/TLS support matrix and consumer overwrite review. No external publication performed.
